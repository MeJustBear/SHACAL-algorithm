# Архитектура `src/`

Документ описывает, **как устроен код в `src/`** и, главное, **почему именно так**.
Структура - результат Этапа 3 из [`docs/roadmap.md`](../docs/roadmap.md): «Разделение
ядра и I/O». Подробный план и обоснования см. там; здесь - практическая карта кода.

## Главная идея: разделение на слои

Код разбит на три слоя с **односторонними зависимостями**:

```
cli  ──►  io      (файлы, BMP)
 │
 └────►  core     (чистый алгоритм)
```

- `core/` не знает **ничего** про файлы, BMP, `std::cout` и платформу.
- `io/` знает про файлы, но **ничего** про детали шифра.
- `cli/` склеивает их вместе и разбирает аргументы командной строки.

Зависимости идут только «сверху вниз»: `core` ни от кого не зависит, `io`
самодостаточен, `cli` использует оба. Обратных зависимостей нет - это и есть
суть разделения.

### Зачем так

1. **Подготовка к биндингам.** Чтобы позже сделать стабильный C-ABI (Этап 5) и
   Python-модуль (Этап 6), нужно ядро, которое не тянет за собой файловый I/O.
   Нельзя из Python звать функцию, которая внутри сама открывает файл и пишет в
   `std::cout`. `core/` уже готов к тому, чтобы его вызывали из любого окружения.
2. **Тестируемость.** Чистые функции над буферами в памяти тривиально покрываются
   тест-векторами (Этап 4): дал на вход байты - получил байты, без временных
   файлов и моков.
3. **Переиспользование.** `core/` собирается в отдельную библиотеку
   `libshacal_core.a`, которую можно прилинковать к CLI, к тестам, к C-ABI - к
   чему угодно.

## Карта каталогов

```
src/
├── core/                  # чистое алгоритмическое ядро  -> libshacal_core.a
│   ├── shacal1.hpp/.cpp   # блочное преобразование, key schedule, be32, ROTL
│   ├── padding.hpp/.cpp   # дополнение PKCS#7 (pad + валидирующий unpad)
│   ├── errors.hpp         # иерархия исключений ядра
│   └── modes/             # режимы сцепления блоков
│       ├── detail.hpp     # внутренние помощники (xor блоков, проверка длины)
│       ├── ecb.hpp/.cpp
│       ├── cbc.hpp/.cpp
│       ├── cfb.hpp/.cpp
│       └── ofb.hpp/.cpp
├── io/                    # файловый/BMP-слой           -> libshacal_io.a
│   ├── streams.hpp/.cpp   # чтение/запись файлов и hex-значений (key/iv/consts)
│   └── bmp.hpp/.cpp       # отделение заголовка BMP
└── cli/                   # точка входа                  -> shacal_cli
    ├── main.cpp           # разбор аргументов, диспетчеризация режимов
    └── stats.hpp/.cpp     # исследовательские метрики (печатают в stdout)
```

## Слой `core/` - чистое ядро

Принципы (закреплены в roadmap, раздел «Чистое ядро»):

- работает только с буферами в памяти (`std::vector<uint8_t>`, `std::array`);
- **не** открывает файлы, **не** пишет в `std::cout`;
- об ошибках сообщает **только** через исключения из `errors.hpp`;
- **раундовые константы передаются аргументом в каждый вызов** - ядро никогда не
  читает `consts.txt` и не зашивает единственный набор внутрь раундовой функции.
  Это принципиально: проект исследовательский, и возможность варьировать константы
  влияет на криптостойкость (см. roadmap).

### `shacal1.hpp/.cpp` - само преобразование

Содержит «математику» шифра, не зависящую от режима:

- типы-обёртки фиксированного размера: `Block` (5 слов), `Key` (16 слов),
  `Schedule` (80 слов), `RoundConsts` (4 слова) - размеры в типе вместо «магических»
  чисел и сырых указателей;
- `load_be32` / `store_be32` - чтение/запись 32-битного слова в big-endian. Они
  заменили прежнюю ручную побайтовую сборку `uint32_t` (старый `read_block`), где
  легко было ошибиться и потерять байт;
- `rotl32` - циклический сдвиг (защищён от сдвига на 0, который раньше был UB);
- `expand_key` - развёртка ключа 16 → 80 слов;
- `encrypt_block` / `decrypt_block` - 80 раундов над одним блоком, по значению
  (никаких `new`/`delete`, никаких утечек).

> **Важно.** Поведение блочного преобразования намеренно сохранено байт-в-байт
> относительно прежней версии (включая унаследованный квирк key schedule, из-за
> которого слово `w[16]` остаётся нулевым). Менять это нельзя без согласования:
> иначе сломается совместимость со старыми зашифрованными данными и тест-векторами.
> Подробности - в комментарии у `expand_key`.

### `padding.hpp/.cpp` - дополнение PKCS#7

Дополнение вынесено в отдельную сущность (а не размазано по `read_block` /
`finalise_res`, как раньше). Используется стандарт **PKCS#7**.

Зачем заменили самодельную схему: у старой были конкретные дефекты -
потеря последнего байта на невыровненных длинах и отсутствие валидации (при
повреждении данных программа падала с `std::length_error` из `resize`). PKCS#7:

- корректен для входов **любой** длины (round-trip всегда сходится);
- при снятии дополнения **проверяет** хвостовые байты и бросает `PaddingError`,
  если они некорректны (повреждённый шифртекст или неверные ключ/IV/константы).

### `errors.hpp` - как ядро сообщает об ошибках

Маленькая иерархия: `Error` → `InvalidArgument`, `PaddingError`. Ядро не печатает
сообщения само - оно бросает типизированное исключение, а уже `cli` решает, как
его показать пользователю. Это и позволяет позже маппить ошибки в коды C-ABI или
в Python-исключения.

### `modes/` - режимы как функции, а не как `namespace` с глобальным состоянием

Каждый режим - это пара свободных функций `*_encrypt` / `*_decrypt` в
`namespace shacal::modes`. Раньше режим выбирался через `using namespace ecb;` -
теперь это просто вызов нужной функции. Все режимы:

- принимают/возвращают `std::vector<uint8_t>`;
- сами применяют PKCS#7 (pad при шифровании, unpad при расшифровании);
- получают ключ/IV/константы аргументами.

`detail.hpp` - внутренние помощники (XOR блоков, проверка кратности длины блоку),
не входящие в публичный API, чтобы не дублировать их в каждом режиме.

## Слой `io/` - работа с файлами

Здесь сосредоточено всё «грязное» взаимодействие с диском, отделённое от шифра.

- `streams.hpp/.cpp` - `read_file` / `write_file` (сырые байты) и
  `read_hex_values` / `write_hex_values` (текстовые файлы ключа, IV и констант в
  формате, совместимом со старыми экспериментами).
- `bmp.hpp/.cpp` - `split_bmp_header`: отделяет 54-байтный заголовок BMP, чтобы
  CLI мог зашифровать только данные изображения, оставив заголовок «видимым»
  (`--preserve-bmp-header`).

`io/` зависит только от стандартной библиотеки и собирается в `libshacal_io.a`.

## Слой `cli/` - точка входа

`main.cpp` - тонкий «дирижёр»:

1. разбирает аргументы командной строки в структуру `Options`;
2. через `io/` читает входной файл, ключ, IV, константы;
3. при `--preserve-bmp-header` отделяет заголовок BMP;
4. вызывает нужную функцию режима из `core/`;
5. через `io/` пишет результат.

`stats.hpp/.cpp` - исследовательские метрики (распределение бит, корреляция
вход/выход). Они **печатают в stdout**, поэтому им место именно в CLI, а не в
чистом ядре.

## Как это собирается

`CMakeLists.txt` отражает слои один-в-один:

| Цель             | Из чего        | Тип                  |
|------------------|----------------|----------------------|
| `shacal_core`    | `src/core/**`  | статическая библиотека |
| `shacal_io`      | `src/io/**`    | статическая библиотека |
| `shacal_cli`     | `src/cli/**`   | исполняемый файл, линкует обе библиотеки |

Артефакты (`build/libshacal_core.a`, `build/libshacal_io.a`, `build/shacal_cli`)
лежат в `build/` и в репозиторий не попадают (см. `.gitignore`) - их пересоздаёт
`cmake --build`.

## Куда это ведёт дальше

Текущее разделение - фундамент для следующих этапов roadmap:

- **Этап 4** - тесты поверх `core/` (чистые функции легко покрыть векторами);
- **Этап 5** - C-ABI поверх `core/` (ядро уже не тянет файловый I/O);
- **Этап 6** - Python-биндинги поверх того же C-ABI/ядра.

Поэтому при доработках важно сохранять границы слоёв: не тащить файловый I/O в
`core/` и не зашивать раундовые константы внутрь алгоритма.
