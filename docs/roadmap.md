# Roadmap: от учебной C++ реализации SHACAL до Python-модуля

Документ описывает поэтапный путь развития проекта: от текущего состояния
(набор C++ исходников, требующих пересборки под каждый режим работы и тип
входных данных) до устанавливаемого через `pip` нативного Python-модуля.

Roadmap построен так, что каждый этап завершается работоспособным, проверяемым
артефактом — и в любой момент можно остановиться и получить пользу от
накопленных изменений.

---

## Исследовательская направленность и раундовые константы

Проект в первую очередь **исследовательский**: цель — изучать SHACAL-1, его
статистические свойства и поведение при вариациях параметров, а не поставить
«готовый продуктовый шифр».

Ключевой настраиваемый параметр — **набор из четырёх раундовых констант**
(как в SHA-1: по одной на каждый диапазон из 20 раундов из 80). Их выбор
**напрямую влияет на криптостойкость** всего алгоритма: дифференциальные и
линейные характеристики, распределение выхода, устойчивость к статистическому
и дифференциальному анализу. Поэтому **возможность изменять раундовые
константы должна сохраняться на всех этапах рефакторинга** — это не временный
костыль, а суть проекта.

Сейчас константы задаются через `consts.txt`; в дальнейшем появятся встроенные
дефолты (значения SHACAL-1) и удобные флаги CLI/Python — но подстановка своего
набора из 4 × `uint32_t` остаётся обязательной на каждом уровне API:

| Уровень        | Как передаются константы (целевое состояние)        |
|----------------|-----------------------------------------------------|
| C++ ядро       | аргумент `const uint32_t*` / `std::span` / структура |
| CLI            | `--round-consts` или `--round-consts-file`          |
| C-ABI          | `shacal_round_consts_t` (`NULL` → дефолт)           |
| Python         | `round_consts=(C0, C1, C2, C3)`                     |

При рефакторинге **нельзя**:

- свести константы к неизменяемому `#define` или зашить их только внутрь
  `encrypt_block` / `decrypt_block` без параметра вызова;
- «оптимизировать» проект за счёт удаления `consts.txt` и файлового/CLI-пути
  без эквивалентной программной подстановки;
- трактовать встроенные значения SHACAL-1 как единственно допустимые — они
  лишь **default** для воспроизведения известных тест-векторов и базового режима.

При шифровании и расшифровании набор констант должен совпадать; исследователь
несёт ответственность за фиксацию использованного набора (sidecar, метаданные
файла, журнал эксперимента) — так же, как сейчас с IV.

## 0. Точка отсчёта (как есть сейчас)

Что есть в репозитории сегодня:

- Алгоритм SHACAL-1: блок 5 × `uint32_t` (160 бит), ключ 16 × `uint32_t`
  (512 бит), расширяемый до 80 × `uint32_t`.
- Четыре режима работы — `ECB.cpp`, `CBC.cpp`, `CFB.cpp`, `OFB.cpp` —
  каждый в собственном пространстве имён.
- Главный файл `main.cpp` управляет поведением через директивы препроцессора:
  - `#define BMP` / `#define TEXT` — тип входных данных;
  - `#define DEBUG_1 / DEBUG_2 / DEBUG_3` — что делать (шифровать, расшифровать,
    round-trip);
  - `using namespace cbc;` — какой режим использовать.
- Пути зашиты в код в Windows-стиле (`..\\bmp_key.txt`, `..\\output_shacal.bmp`).
- Раундовые константы читаются из внешнего файла `consts.txt` — **намеренно**,
  чтобы менять набор констант без пересборки и оценивать влияние на стойкость
  (см. раздел «Исследовательская направленность и раундовые константы»).
- Алгоритмическое ядро перемешано с файловым и BMP-I/O.

Известные технические долги, которые надо устранить по пути:

- `std::exception("...")` — расширение MSVC, не компилируется на GCC/Clang.
- Утечки памяти: `new std::vector<...>` внутри функций + `delete &result`
  у вызывающего.
- `function(x, y, z, i)` не имеет `return` во всех ветках при некорректном `i`
  (UB).
- `pow(2, 32)` в горячем цикле — заменить маской / естественным переполнением
  `uint32_t`.
- `goto label` в `read_block` — переписать.
- Самодельный «генератор ключей» поверх `default_random_engine` —
  криптографически непригоден.

## Этап 1. Стабилизация и кроссплатформенная сборка

**Цель:** собирать существующий код одной командой на Linux/macOS/Windows,
без правки исходников ради смены режима.

1. Добавить `CMakeLists.txt` верхнего уровня:
   - стандарт C++17;
   - цель `shacal_cli` из существующих `.cpp`;
   - предупреждения как ошибки (`-Wall -Wextra -Wpedantic` / `/W4`).
2. Привести код к компилируемости вне MSVC:
   - заменить `std::exception("msg")` на `std::runtime_error("msg")`
     (`<stdexcept>`);
   - убрать `using namespace std;` из заголовков, оставить только в `.cpp`;
   - убрать `pow(2, 32)` — операции и так идут в `uint32_t`, переполнение
     по модулю 2³² «бесплатное».
3. Пути к файлам — только через аргументы командной строки и относительные
   пути в стиле POSIX (`/`); никаких `..\\`.
4. Добавить **встроенные значения по умолчанию** (значения SHACAL-1), **не
   отменяя** возможность подставить свой набор в рантайме — это требование
   исследовательского проекта (см. раздел выше):
   ```cpp
   // Дефолтные раундовые константы SHACAL-1 (как в SHA-1).
   // НЕ хардкод финального поведения — лишь default'ы для штатного режима.
   constexpr std::array<uint32_t, 4> kShacal1DefaultRoundConsts = {
       0x5A827999, 0x6ED9EBA1, 0x8F1BBCDC, 0xCA62C1D6,
   };
   ```
   Сигнатуры `encrypt_block` / `decrypt_block` / режимов принимают указатель
   на 4 × `uint32_t` (или `std::span`); `NULL` / пустой optional → дефолт.
   Чтение `consts.txt` можно оставить как один из способов загрузки для CLI
   и для совместимости с текущими экспериментами; убрать файл из репозитория
   **нельзя**, пока не обеспечен эквивалент через API и флаги.
5. Закрыть UB в `function()` — добавить `default`/финальный `return` и
   `assert(i < 80)`.
6. Завести `.editorconfig`, `.clang-format`, `.gitignore` (build-дирректории,
   `*.exe`, `*.obj`).

**Артефакт этапа:** `cmake -B build && cmake --build build` собирает один
бинарник `shacal_cli` на любой ОС.

## Этап 2. CLI вместо `#define`

**Цель:** убрать пересборку при смене режима/направления/типа данных.

1. Спроектировать CLI (например, через [`CLI11`](https://github.com/CLIUtils/CLI11)
   как header-only зависимость или вручную):
   ```
   shacal_cli encrypt --mode cbc --key key.bin --iv iv.bin -i in.bmp -o out.bin
   shacal_cli decrypt --mode cbc --key key.bin --iv iv.bin -i out.bin -o restored.bmp
   shacal_cli keygen --out key.bin
   ```
2. Аргумент `--mode` принимает `ecb | cbc | cfb | ofb` и в рантайме выбирает
   нужную реализацию (через `enum class Mode` + `switch`/таблицу функций).
3. Удалить из `main.cpp` все `#define BMP / TEXT / DEBUG_*` и захардкоженные
   пути.
4. Тип данных перестаёт влиять на логику шифрования: алгоритм работает
   с потоком байт, BMP-заголовок (если нужно сохранять «видимым» —
   опционально) обрабатывается отдельной утилитой `--preserve-bmp-header`.
5. **Раундовые константы — параметр запуска** (обязательно для исследований
   стойкости). Добавить два взаимоисключающих флага:
   - `--round-consts C0,C1,C2,C3` — четыре `uint32_t` в hex (например,
     `--round-consts 0x5A827999,0x6ED9EBA1,0x8F1BBCDC,0xCA62C1D6`);
   - `--round-consts-file path` — файл с четырьмя hex-значениями
     (совместимость со старым `consts.txt`).
   Если ни один не указан — используются встроенные дефолты. Команда
   `decrypt` принимает те же флаги: расшифровать получится только тем же
   набором, которым шифровали. Имеет смысл записывать использованные
   константы в шапку выходного файла или в отдельный sidecar — так же,
   как сейчас обстоит дело с IV.

**Артефакт этапа:** один бинарник, все параметры через флаги, никакой
пересборки.

## Этап 3. Разделение ядра и I/O

**Цель:** вычленить чистый алгоритмический слой, не знающий ни про файлы,
ни про BMP. Это обязательный шаг перед биндингами.

Целевая структура каталогов:

```
shacal/
├── core/                  # чистая логика, без I/O
│   ├── shacal1.hpp/.cpp   # encrypt_block / decrypt_block / key schedule
│   ├── modes/
│   │   ├── ecb.hpp/.cpp
│   │   ├── cbc.hpp/.cpp
│   │   ├── cfb.hpp/.cpp
│   │   └── ofb.hpp/.cpp
│   └── padding.hpp/.cpp   # PKCS#7 (или текущая схема — но как функция)
├── io/                    # файловый/BMP-слой
│   ├── bmp.hpp/.cpp
│   └── streams.hpp/.cpp
├── cli/
│   └── main.cpp
└── tests/
```

Принципы слоя `core`:

- Работает только с буферами в памяти: `std::span<const std::byte>` /
  `std::span<std::byte>` (или `const uint8_t*` + `size_t` для C++17).
- Не открывает файлы, не пишет в `std::cout`, не бросает исключения через
  `std::exception("…")`.
- Все аллокации — снаружи или через переданный `std::pmr::memory_resource` /
  output-буфер фиксированного размера.
- Ни одного `using namespace ecb;` — режимы стали типами/функциями
  (`shacal::modes::cbc_encrypt(...)`).
- Раундовые константы передаются **в каждый вызов** шифрования/расшифрования
  (или через контекст `Cipher` с полем `round_consts`); ядро не читает
  `consts.txt` и не зашивает единственный набор внутрь раундовой функции.

По ходу:

- Починить утечки памяти — больше никаких `new std::vector<>` +
  `delete &result`. Возвращаем по значению (RVO/move).
- Заменить ручную побайтовую сборку `uint32_t` (см. `read_block`) на
  понятные функции `load_be32` / `store_be32`.
- Padding выделить в отдельную сущность; зафиксировать выбор (рекомендуется
  PKCS#7 для совместимости с экосистемой), либо сохранить текущую схему,
  но описать её в `docs/`.

  > **Известные дефекты текущей схемы дополнения** (выявлены при переходе на
  > CLI на Этапе 2; код `read_block` / `finalise_res` / `create_special_block`
  > намеренно не менялся, чтобы сохранить поведение алгоритма):
  >
  > 1. **Потеря последнего байта на невыровненных входах.** Round-trip сходится
  >    идеально только когда длина данных кратна размеру блока (20 байт). На
  >    некоторых невыровненных длинах теряется последний байт — например, вход
  >    57 байт восстанавливается как 56. Причина — рассинхрон между маркером,
  >    который `read_block` встраивает в последнее слово неполного блока, и тем,
  >    как `finalise_res` по этому маркеру урезает результат (она убирает целое
  >    слово, в котором ещё лежал реальный байт данных). Дополнительный фактор —
  >    декремент `current_int_count` в `read_block`, теряющий учёт частично
  >    заполненного слова.
  > 2. **Нет валидации маркера дополнения.** `finalise_res` доверяет последнему
  >    слову и делает `result.resize(result.size() - count / BLOCK_SIZE)` без
  >    проверки. При неверном наборе раундовых констант (или повреждённом
  >    шифртексте) `count` оказывается мусорным, и `resize` бросает
  >    `std::length_error` (`vector::_M_default_append`). Сейчас это исключение
  >    лишь перехватывается в CLI; в `core/` нужна явная ошибка
  >    «некорректный padding».
  > 3. **Намеренный fall-through в `finalise_res`** (`switch` без `break` в
  >    `case 1/2/3`) даёт предупреждение компилятора; при выделении padding в
  >    отдельную функцию переписать на понятную сборку хвостовых байт и
  >    промаркировать осознанный fall-through через `[[fallthrough]]` (или убрать).
  >
  > Рекомендация: при выделении padding перейти на PKCS#7 (или строго
  > специфицировать текущую схему) и закрыть пункты 1–3 регрессионными тестами
  > на Этапе 4 (длины 0, 1, BLOCK-1, BLOCK, BLOCK+1 и т.д.).

**Артефакт этапа:** статическая библиотека `libshacal_core.a` без зависимостей
от файлового I/O, плюс тонкая `libshacal_io.a` для CLI.

## Этап 4. Тесты и тест-векторы

**Цель:** доказать, что рефакторинг ничего не сломал, и зафиксировать
поведение перед выходом «наружу».

1. Подключить тест-фреймворк: GoogleTest или Catch2 (рекомендуется Catch2
   как header-only).
2. Написать тесты для `core/`:
   - известные тест-векторы SHACAL-1 (один блок: ключ + plaintext → ciphertext);
   - round-trip: `decrypt(encrypt(x, key, iv), key, iv) == x` для каждого
     режима, для случайных входов разной длины (включая 0, 1, BLOCK-1, BLOCK,
     BLOCK+1 байт);
   - проверка key schedule (расширение 16 → 80 слов);
   - проверка `load_be32` / `store_be32` на известных значениях.
   - **Регрессия по дефектам padding (см. Этап 3).** Отдельно проверить
     невыровненные длины, на которых сейчас теряется последний байт (в т.ч.
     ровно 57 байт), и зафиксировать, что после починки `len(decrypt(encrypt(x)))
     == len(x)` для **любой** длины, а не только кратной блоку. Прогнать
     перебор длин от 0 до 2×BLOCK для каждого режима.
   - **Валидация дополнения.** Убедиться, что повреждённый шифртекст или неверный
     набор раундовых констант приводит к явной ошибке «некорректный padding», а
     не к `std::length_error` из `finalise_res`/`resize`.
   - **Совпадение с эталоном Этапа 2.** Для длин, кратных блоку (где старое
     поведение корректно), сравнить выход нового `core/` с выходом текущего CLI
     при одинаковых ключе/IV/константах — гарантия, что рефакторинг ничего не
     сломал.
3. Подключить санитайзеры в отдельной сборочной конфигурации
   (`-fsanitize=address,undefined`) — обязательно прогнать тесты под ASan/UBSan,
   чтобы вычистить остатки UB из старого кода.
4. Поднять GitHub Actions:
   - матрица: `{ubuntu-latest, macos-latest, windows-latest} × {gcc, clang, msvc}`;
   - шаги: configure, build, test;
   - артефакт — собранный CLI для каждой платформы.

**Артефакт этапа:** зелёный CI на трёх ОС, набор тест-векторов в
`tests/vectors/`.

## Этап 5. Стабильный C-ABI

**Цель:** дать любому языку (Python, Rust, Go, …) простой и стабильный путь
к ядру без необходимости тащить C++ ABI.

Создать `core/c_api.hpp` / `core/c_api.cpp` с интерфейсом примерно такого
вида:

```c
#ifdef __cplusplus
extern "C" {
#endif

typedef enum {
    SHACAL_MODE_ECB = 0,
    SHACAL_MODE_CBC = 1,
    SHACAL_MODE_CFB = 2,
    SHACAL_MODE_OFB = 3,
} shacal_mode_t;

typedef enum {
    SHACAL_OK = 0,
    SHACAL_ERR_INVALID_KEY_SIZE = 1,
    SHACAL_ERR_INVALID_IV_SIZE  = 2,
    SHACAL_ERR_INVALID_PADDING  = 3,
    SHACAL_ERR_BUFFER_TOO_SMALL = 4,
    /* ... */
} shacal_status_t;

/* Возвращает требуемый размер выходного буфера для encrypt/decrypt. */
size_t shacal_encrypt_output_size(shacal_mode_t mode, size_t in_len);
size_t shacal_decrypt_output_size(shacal_mode_t mode, size_t in_len);

/* Раундовые константы. NULL => использовать встроенные дефолтные SHACAL-1.
   Если указано — массив из ровно 4 значений uint32_t. */
typedef struct {
    const uint32_t* values;   /* указатель на 4 × uint32_t или NULL */
    size_t          count;    /* должен быть 4, если values != NULL */
} shacal_round_consts_t;

shacal_status_t shacal_encrypt(
    shacal_mode_t                mode,
    const uint8_t*               key,    size_t key_len,    /* 64 байта (512 бит) */
    const uint8_t*               iv,     size_t iv_len,     /* 20 байт или 0 для ECB */
    const shacal_round_consts_t* round_consts,              /* NULL => дефолт */
    const uint8_t*               in,     size_t in_len,
    uint8_t*                     out,    size_t* out_len);  /* in/out: capacity / written */

shacal_status_t shacal_decrypt(/* симметрично, тоже принимает round_consts */);

#ifdef __cplusplus
}
#endif
```

Плюс:

- собирать `libshacal.{a,so,dylib,dll}` с этим ABI;
- описать инвариант: «64-битный ключ принимается как 64 байта в big-endian
  слов», «IV — 20 байт», «padding — PKCS#7», «раундовых констант — ровно 4
  штуки `uint32_t`, при `NULL` подставляются дефолты SHACAL-1»;
- зафиксировать SemVer для C-ABI отдельно от внутреннего C++ API.

**Артефакт этапа:** `shacal.h` + общая библиотека, ABI-стабильный.

## Этап 6. Python-биндинги

**Цель:** получить нативный Python-модуль `shacal`.

### 6.1. Выбор инструмента

Рекомендация — **pybind11** (зрелый, документированный, header-only,
интегрируется с CMake). Альтернативы:

- **nanobind** — быстрее компилируется и даёт меньшие артефакты, но требует
  Python ≥ 3.8 и C++17/20.
- **Cython** — оправдан, если нужна только обёртка вокруг C ABI без C++.
- **ctypes/cffi** — нулевые зависимости при сборке Python-стороны, но
  ручная работа с памятью и типами; терпимо для простого ABI.

Дальше предполагаем pybind11.

### 6.2. Структура проекта

```
shacal-py/
├── pyproject.toml          # PEP 517/518, build-system = scikit-build-core
├── CMakeLists.txt          # подключает core/ как подпроект
├── src/
│   └── shacal/
│       ├── __init__.py
│       ├── _shacal.pyi     # type stubs
│       └── _shacal*.so     # собирается из bindings.cpp
├── bindings/
│   └── bindings.cpp        # pybind11
└── tests/
```

### 6.3. Python API

Минимальный функциональный API:

```python
import shacal

ct = shacal.encrypt(plaintext, key=key, mode="cbc", iv=iv)
pt = shacal.decrypt(ct,        key=key, mode="cbc", iv=iv)

key = shacal.generate_key()      # secrets.token_bytes(64) под капотом
iv  = shacal.generate_iv()
```

Раундовые константы — необязательный параметр; по умолчанию — дефолтные
SHACAL-1, но можно передать свои четыре `uint32_t` для исследовательских
сценариев (анализ статистических свойств, проверка стойкости при
изменённых константах):

```python
# tuple из ровно 4 значений uint32_t
custom = (0x5A827999, 0x6ED9EBA1, 0x8F1BBCDC, 0xCA62C1D6)

ct = shacal.encrypt(plaintext, key=key, mode="cbc", iv=iv,
                    round_consts=custom)
pt = shacal.decrypt(ct,        key=key, mode="cbc", iv=iv,
                    round_consts=custom)   # должен совпадать с тем, что при шифровании

# доступ к дефолтам — для прозрачности
shacal.DEFAULT_ROUND_CONSTS  # (0x5A827999, 0x6ED9EBA1, 0x8F1BBCDC, 0xCA62C1D6)
```

Важно: при расшифровке набор констант обязан совпасть с использованным при
шифровании, иначе результат — мусор (это ответственность вызывающего; ABI
не хранит константы внутри ciphertext).

Объектный API (для повторного использования и стрима):

```python
cipher = shacal.Cipher(key=key, mode=shacal.Mode.CBC, iv=iv)
ct = cipher.encryptor().update(chunk1) + cipher.encryptor().update(chunk2) + ...
```

Требования к биндингу:

- принимать `bytes`, `bytearray`, `memoryview` (буфер-протокол) без копий
  на входе;
- возвращать `bytes`;
- освобождать GIL на тяжёлых операциях (`py::gil_scoped_release`);
- маппить `shacal_status_t` в Python-исключения (`ValueError`,
  `shacal.PaddingError`, и т.д.).

## Этап 9. Качество и расширения (по желанию)

- Property-based тесты на Python-уровне через Hypothesis:
  `decrypt(encrypt(x, k, iv), k, iv) == x` для произвольных `x`, `k`, `iv`.
- Бенчмарки (`pytest-benchmark`) — сравнение режимов и сравнение с
  «эталонной» реализацией на чистом Python.
- Опциональные оптимизации ядра: SIMD-развёртка раундов, многопоточная
  обработка независимых блоков (ECB/CTR).
- Добавить режим **CTR** — он мало стоит после рефакторинга и даёт
  параллелизм «бесплатно».
- Async-friendly API: `await cipher.encrypt_file(path)` через `asyncio.to_thread`.

## Принципы, которых придерживаемся по пути

1. **Исследовательский фокус.** Проект существует, чтобы варьировать параметры
   (прежде всего раундовые константы) и оценивать влияние на криптостойкость;
   рефакторинг не должен это ограничивать.
2. **Не ломать поведение алгоритма.** На каждом этапе round-trip и
   тест-векторы должны проходить; сравнивать выход новой версии с
   эталонным выходом старой версии для одинаковых ключа/IV/входа и **того же
   набора раундовых констант**.
3. **Один этап — один PR.** Этапы независимы и сливаются по очереди.
4. **Сначала корректность, потом производительность.** Все оптимизации —
   после этапа 4 (есть тесты, можно безопасно ускорять).
5. **Чистое ядро.** `core/` не знает про файлы, BMP, `std::cout` и
   платформу. Это обязательное условие для биндингов; при этом ядро **обязано**
   принимать раундовые константы как аргумент, а не читать их из файла само.
6. **Раундовые константы — параметр, не хардкод.** Они влияют на стойкость
   всего алгоритма; на каждом уровне API (C++ ядро, CLI, C-ABI, Python) их
   можно переопределить; встроенные значения SHACAL-1 — лишь default.
7. **Честное предупреждение пользователю.** SHACAL-1 — учебный/исторический
   шифр; для продакшн-криптографии — AES/ChaCha20. README и документация это
   явно подсвечивают.
